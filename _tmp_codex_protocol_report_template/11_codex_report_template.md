# Codex Final Report Template

## 1. 要約
今回何を調査し、どの結論に至り、実装したのか、または保留にしたのかを短くまとめる。

## 2. 背景と目的
この案件の狙い、今回の第1段階で何を重視するか、将来の OpenRadioss / OpenFOAM 連携をどう見据えるかを書く。

## 3. 調査対象と調査方法
どのディレクトリ、どの app、どの compose、どの Portal 構成、どの既存カードを調査したかを書く。

## 4. 既存資産調査結果
既存アプリ、既存コード、既存 UI、既存サービス、既存カード、既存 route、既存 compose 構成を整理する。

## 5. 類似アプリ一覧
今回の要求に近い既存アプリや既存機能を列挙し、それぞれ何が近いかを書く。

## 6. 競合・コンフリクト一覧
path、slug、port、service、container、volume、env var、依存関係、責務重複などの観点で整理する。

## 7. 比較検討
全面導入、一部融合導入、既存採用優先、保留の4案を比較表で示す。

## 8. 推奨方針
最終的にどの案を採用したか、その理由、採用しなかった案の理由も書く。

## 9. 詳細設計
画面構成、導線、3Dモデル入力、ステージ表現、Portalカード、kinematics_hub との関係、将来 solver 連携点を書く。

## 10. DR結果
DRで確認した項目、懸念、対策、Go / 条件付きGo / 保留 の判断を書く。

## 11. 実装計画
実装順序、変更範囲、影響範囲、ロールバック方針を書く。

## 12. 実装結果
実際に何を実装したか、何を変更したか、何を追加したかを書く。

## 13. 変更ファイル一覧
新規追加ファイル、既存変更ファイル、Docker Compose 変更、Portal カード変更を整理する。

## 14. テスト結果
確認手順、期待結果、実確認結果、未確認項目を書く。

## 15. 未実装項目と制約
今回やっていないこと、今回見送ったこと、技術的制約を書く。

## 16. 将来拡張案
OpenRadioss 連携案、OpenFOAM 連携案、必要追加データ、次フェーズ候補を書く。

## 17. 保留時の再開条件
保留判断した場合のみ、再開に必要な条件、前提、次アクションを書く。

## 18. 結論
ユーザー価値、今回の成果、次に何をすべきかを短くまとめる。
