この作業は、OpenClaw / Portal / Docker Compose / 既存カード追加前提の実装案件として、自律実行で進めてください。  
ただし最重要ルールとして、いきなり新規実装に入らないこと。最初に必ず、既存の OpenClaw / Portal / apps / Docker Compose / 可視化系 / CAD系 / CAE系 / kinematics_hub / OpenRadioss / OpenFOAM 関連の実装を横断調査し、競合、重複、衝突、流用可能性を確認してください。  
今回の目的は、ユーザーが更新した3Dモデルを起点として、金型設計検討につながる支援アプリを構築することです。ただし今回の第1段階では、厳密なFEM主計算は不要です。まずは、工程ごとにどのように形状が変化するかをユーザーに伝える視覚化アプリを重視してください。プレス金型向けでは http://localhost:8088/apps/kinematics_hub/index.html を活用し、どのステージでどのような製品形状になるかが直感的に分かるようにしてください。  
そのうえで将来拡張として、OpenRadioss や OpenFOAM など Portal ダッシュボード上の既存アプリへ工程条件・材料条件・形状条件を受け渡し、詳細計算につなげられる構造を最初から考慮してください。

【最初に必ず行う意思決定】  
調査のあと、次の4案を必ず比較してください。  
1. 全面導入: 新規アプリを主軸に大きく導入  
2. 一部融合導入: 既存アプリや kinematics_hub に拡張実装  
3. 既存採用優先: 新規追加を最小にして既存機能を再編・再利用  
4. 今回は保留: 調査結果と設計のみ整理し、実装を見送る  
各案について、メリット、デメリット、技術リスク、運用リスク、既存資産影響、実装工数、保守性、Portal統合容易性、将来の OpenRadioss / OpenFOAM 連携しやすさを比較してください。  
最初にこの判断を行い、推奨案を1つ選んでから次工程へ進むこと。  
最初の判断なく実装に入らないでください。

【推奨方針の原則】  
- 既存資産が活かせるなら、置換よりも融合・拡張を優先  
- 既存 kinematics_hub が活用可能なら、まず流用可能性を評価  
- 既存 Portal のカード構造・導線・カテゴリーに自然に統合  
- 破壊的変更は避ける  
- まずは小さく価値を出す  
- 将来の詳細計算連携に備えた拡張性を残す  
- UI は工程理解、形状変化理解、説明しやすさを優先  
- 第1段階では FEM 精度より可視化価値を優先
