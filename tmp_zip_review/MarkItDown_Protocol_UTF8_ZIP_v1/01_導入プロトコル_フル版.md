# MarkItDown 導入プロトコル フル版

## 1. 目的
MarkItDown を、単なるファイル変換ツールとしてではなく、**LLM/RAG 前処理標準化モジュール**として導入する。

本プロトコルでは、導入する・しないの最終判断は**受け取り側の Codex または Claude**に委ねる。  
ただし、判断に必要な材料が欠けないよう、実装候補・接続点・注意点まで整理する。

## 2. 導入価値
MarkItDown の価値は、見た目の再現ではなく、**文書構造を壊しにくい Markdown 化**にある。

- 見出し構造の保持
- 箇条書きの保持
- 表の保持
- RAG 用チャンク分割との相性が良い
- LLM が section 単位で意味を取りやすい

## 3. 想定ユースケース
### 3.1 品質保証
- 内部監査報告書
- 是正処置報告書
- 顧客提出資料
- 作業標準書
- IATF 関連文書

### 3.2 製造技術
- めっき仕様書
- SDS
- リフロー条件票
- 設備マニュアル
- 成形条件表
- プレス条件表

### 3.3 データ解析
- Excel の測定一覧
- 異常履歴
- P-chart / SPC 元資料
- 複数資料の横断検索用前処理

## 4. 導入方針
### 段階A：単体評価
1. 代表サンプルを 10〜20 件集める
2. MarkItDown で Markdown 化
3. 変換品質を評価
4. 表・見出し・箇条書き・画像周りの崩れを確認

### 段階B：半自動化
1. 監視フォルダを作る
2. 新規ファイル投入で自動変換
3. 変換結果を `processed_md` に保存
4. ログを残す

### 段階C：RAG 統合
1. Markdown をチャンク分割
2. embedding 生成
3. Qdrant 等に投入
4. Paperless / OpenClaw / 検索 UI と接続

## 5. 推奨アーキテクチャ
```text
[raw_docs]
  ├─ pdf
  ├─ docx
  ├─ xlsx
  ├─ pptx
  ├─ images
  └─ zip

        ↓

[MarkItDown]
        ↓
[Markdown 出力]
        ↓
[前処理]
  - メタデータ付与
  - セクション分割
  - 表の整形
  - 必要に応じOCR補助
        ↓
[Embedding]
        ↓
[Vector DB / RAG]
        ↓
[OpenClaw / Antigravity / Codex / Claude]
```

## 6. 最低限の導入手順
### 6.1 Python 仮想環境
```bash
python -m venv .venv
.venv\Scripts\activate
pip install -U pip
pip install markitdown
```

### 6.2 単体変換
```bash
markitdown sample.pdf > sample.md
```

### 6.3 Python API
```python
from markitdown import MarkItDown

md = MarkItDown()
result = md.convert("sample.pdf")
print(result.text_content)
```

## 7. Windows 運用時の注意
1. PowerShell の既定エンコーディング差異に注意
2. 保存テキストは UTF-8 を基本とする
3. 日本語ファイル名の入出力試験を必ず行う
4. ZIP 内ファイル名の日本語検証を行う
5. OneDrive 同期下ではファイルロックに注意

## 8. 業務向け評価観点
| 観点 | 評価内容 |
|---|---|
| 見出し保持 | 節構造が保たれるか |
| 表保持 | 行列が壊れにくいか |
| 箇条書き保持 | 手順書の列挙が崩れないか |
| OCR併用性 | スキャン文書でも後段で使えるか |
| 処理速度 | 日常バッチに耐えるか |
| トークン効率 | 冗長なノイズが少ないか |
| 例外処理 | 壊れたPDFや画像混在ZIPに耐えるか |

## 9. Paperless / OpenClaw 連携の考え方
- OCR 後のテキストが弱い場合の補助ではなく、**文書構造再表現**として使う
- OpenClaw に直接 Office/PDF を投げる前に Markdown 化
- RAG の recall / precision 両方の改善を狙う

## 10. 向いている文書 / 向いていない文書
### 向いている
- 議事録
- 規格書
- 監査資料
- 手順書
- Excel ベースの一覧表
- PowerPoint の説明資料

### 苦手になりやすい
- 複雑な図面
- 幾何公差の解釈が必要な図
- スキャン品質の低い帳票
- 数式だらけの資料
- 画像主体で文字が少ない資料

必要なら以下を併用する。
- Docling
- OCR
- VLM
- 独自パーサー

## 11. 導入可否判断を Codex / Claude に委ねる際の条件
受け取り側は、以下を必ず判定すること。

1. 現在の ingest パイプラインと競合しないか
2. 既存 OCR / Docling / Paperless との責務分離が明確か
3. 変換結果の再現性が取れるか
4. バッチ失敗時のリトライが実装しやすいか
5. 日本語文書の品質が許容範囲か
6. Windows と Docker の両方で無理なく運用できるか

## 12. 最小PoCの成功条件
- PDF 5件
- Word 3件
- Excel 3件
- PowerPoint 3件
- ZIP 2件

に対して、

- 変換成功率 90%以上
- 見出し保持 80%以上
- 表保持 70%以上
- 実務検索改善を最低 1 件以上確認

- 変換終了時刻

- 成否

- 出力サイズ
- 文字数
- 表数の概算
- 見出し数の概算
