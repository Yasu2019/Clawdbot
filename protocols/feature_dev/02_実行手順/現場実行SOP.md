# 現場実行SOP

## 0. 実行前チェック
- 対象リポジトリは正しいか
- ブランチは分離されているか
- 本番秘密情報は露出していないか
- DB 接続は読み取り専用か
- 依頼内容に目的・制約・出力物があるか

## 1. 依頼文を作る
最低限、次を含める。
- 目的
- 背景
- 対象
- 制約
- 出力物
- 受入条件
- 禁止事項

### 最小テンプレ
```text
/feature-dev
目的:
背景:
対象:
制約:
出力物:
受入条件:
禁止事項:
```

## 2. Explorer の結果を確認する
確認ポイント:
- どのファイルが影響範囲か
- 既存実装はどこにあるか
- 同機能や類似機能の重複がないか
- 既存の命名規則や実装規約があるか
- 変更すると壊れそうな場所はどこか

## 3. Architect の提案を比較する
最低でも以下を比較させる。
- 最小変更案
- 実用バランス案
- 拡張性重視案

比較観点:
- 変更量
- 影響範囲
- テスト容易性
- 将来の保守性
- 既存構成との整合性

## 4. 採用案を固定する
採用時に明記する。
- 採用案の名前
- 採用理由
- 不採用案を見送る理由
- 今回見送る拡張

## 5. 実装させる
この時点で初めてコード変更。
必ず以下も出させる。
- 変更ファイル一覧
- 要点サマリ
- テスト項目
- リスク
- ロールバック方法

## 6. Reviewer の指摘を扱う
採用条件:
- 根拠が明示されている
- 再現または確認方法がある
- 設計意図と矛盾しない
- 優先度が説明されている

## 7. まとめを残す
最低限残す内容:
- 目的
- 採用案
- 変更ファイル
- テスト結果
- 未解決リスク
- 次回課題

## 8. 受入判定
次の全てを満たしたら仮受入。
- 要求機能を満たす
- 既存機能を壊していない
- ログまたはエラー処理がある
- テスト方法が明記されている
- 禁止事項に抵触していない

## 9. 本番化前ゲート
- ステージング検証
- バックアップ取得
- ロールバック確認
- 関係者説明
- 監査が必要な場合は記録保全
