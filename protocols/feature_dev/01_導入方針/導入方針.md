# 導入方針

## 1. なぜ導入するか
feature-dev は、AI を「一人のコーダー」として扱うのではなく、
**調査・設計・レビューを分担するチーム**として扱うための実行様式です。

品質保証の視点では、次の効果があります。

- 現状把握なしの実装を減らせる
- 最小変更案と拡張案を比較できる
- レビュー根拠を残しやすい
- 受入条件を先に固定できる
- 修正のやり直し回数を減らせる

## 2. 品証部門での位置づけ
feature-dev は、実務的には以下に相当します。

- Explorer: 現状調査、現物確認、影響範囲確認
- Architect: 改善案立案、変更案比較、実装方針選定
- Reviewer: 監査、妥当性確認、抜け漏れチェック

## 3. 適用対象
適用しやすいもの:
- 既存社内ツールの機能追加
- Excel/VBA ツールの改修
- Python 集計スクリプト
- Portal カード追加
- ダッシュボード化
- 監査資料生成
- CSV / SQL 読み取り分析
- RAG 検索補助ツール

適用しにくいもの:
- 要件がほぼ未定義
- 仕様より試行錯誤が中心の研究コード
- 外部APIや本番DBに強い副作用を与える実装
- 権限、法令、監査責任が未整理のままの自動更新処理

## 4. 導入原則
1. 実装より先に探索と設計を行う
2. 変更範囲はなるべく小さく始める
3. DB は原則 read only
4. 既存 Portal / Docker / Compose と競合させない
5. テスト・受入条件・ロールバック方法を先に決める
6. 決定事項をまとめに残す
7. 監査対象業務はレビュー証跡を残す

## 5. 期待値の置き方
feature-dev を使っても、最終責任は人が持ちます。
ただし、人が見るべき場所を大幅に絞れるのが価値です。

狙うべき状態:
- 手戻りが減る
- レビュー観点が揃う
- 実装理由を説明できる
- 再利用できるプロトコルが蓄積する

避けるべき状態:
- 毎回ゼロから長文で説明する
- 曖昧な指示のまま実装開始する
- 「AI がそう言った」で採用する
- 本番データに直接触る
