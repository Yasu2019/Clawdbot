# INC-195 / T090 — Red LAVIE r6 stopped early; WSL lifetime guard

## Summary

Red LAVIE r6 (`/home/yns-lavie/openfoam_runs/box_roundhole_r17_red_preflight_r6_20260919`) had `preflight_started.json` but no `preflight_result.json`; its log reached only `Time=4.4e-06`, and the unit stopped after about 16 seconds. At later audit, Ubuntu/Docker WSL and solver processes were stopped. The exact trigger is not proven. This was not a valid completed result and is not evidence for resuming from a verified checkpoint. Existing r1-r5 were preserved.

## 5-Why

1. Why no completed preflight? The terminal result artifact was never produced.
2. Why did the run stop before useful progress? The observed worker/unit lifetime was only about 16 seconds.
3. Why could the workload be that short-lived? The lifecycle owner may have been tied to a WSL or remote-session lifetime.
4. Why was that possible? A systemd unit alone does not keep WSL alive, and remote-started processes can end with their session.
5. Why is the exact r6 cause not stated as certain? No complete process/session event trace was captured at the moment of stop; architecture docs establish risk, not this event's trigger.

## Fishbone / causal branches

- Host/session: WSL shutdown, SSH disconnect, logoff/power state (plausible; exact event unconfirmed).
- Orchestration: no proven independent keepalive owner/readiness gate in the prior launcher design.
- Solver/numerics: log shows early simulation time, but captured evidence does not establish a solver fatal error as the stopping trigger.
- Observability: start artifact exists, terminal manifest absent; capture of lifecycle events is incomplete.
- Case/data: existing r1-r5 retained; no evidence that r6 reused or overwrote them.

## Countermeasures and forbidden actions

- Implemented locally: unique interactive Task Scheduler worker, WSL readiness marker before solver dispatch, bounded probes/dispatch, final monitor status/exit/output in the host manifest, duplicate-unit refusal, and cleanup only after exact task-action fingerprint validation.
- The worker parses the runner JSON schema and allowed `stop_reason` values (up to five bounded retries for an in-progress write); a written result is no longer mislabeled as successful completion. Target-time completion, terminal non-success, invalid result, no active unit, and missing result have distinct host-manifest states.
- The launcher also audits the entire WSL process family (`foamRun`/`mpirun`) before Task Scheduler registration; any active older solver causes fail-closed refusal regardless of the caller's unit name.
- Verified locally: PowerShell AST parse PASS and 25 focused launcher/preflight/checkpoint tests PASS, including embedded Bash syntax, result classification, task cleanup mocks, and concurrency-refusal ordering. `-ValidateOnly` accepts a valid plan and rejects `NaN` without WSL/task/solver calls. Pre-change backup commits `74e1e4fb7e` and `8060cf0d35`; initial archive SHA256 `07EF620386BF14367955E4D2A59AAF4A43097FB21B6822485731E69217596C84`.
- Before Red deployment: run a no-solver lifecycle smoke on a new generation and verify task state, WSL readiness, manifest, worker exit, and cleanup. Revised launcher is not yet deployed or live-tested.
- Do not kill, replace, or reuse r1-r5, old scheduled tasks, or any solver generation without explicit approval and identity verification.
- The task requires an interactive logged-in Windows user; it does not provide recovery across Windows power-off. Do not describe it as autonomous reboot recovery.
