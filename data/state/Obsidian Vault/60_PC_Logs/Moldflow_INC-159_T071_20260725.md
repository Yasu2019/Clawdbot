# Moldflow MCP が使えない — Synergy がスクリプトエラーのモーダルに占有されていた

## Summary

| 区分 | 内容 |
|---|---|
| NG trial | Dynabook (`DESKTOP-UOVCG4T` / `100.98.133.40`) の Moldflow MCP ブリッジが停止。起動後もアクティブstudy系ツールが全て ActiveX 429。`probe_com` は30秒×2回タイムアウト後、約150秒でようやく成功するが `Version : (unavailable)`。 |
| 真因 | Synergy 2010 GUI (PID 6688) が `Internet Explorer_TridentDlgFrame` クラスの「スクリプト エラー」モーダルダイアログに占有され、メインウィンドウが `enabled=False`。1つ閉じると別ハンドルで即再生成される**ループ状態**。 |
| OK trial | Synergyを対話セッション1で強制再起動（新PID 3884）。ブリッジ 0.8.5 を同セッションで再起動。`probe_com` が 32/64bit 両方で成功し `Version : 2010` を取得、`inspect_state` が `ok:true`。読み取り一式 117秒 → 36秒。 |
| Impact | K10/Cursor から Moldflow を一切制御できなかった。ディスク上の `box_study_3` は無改変、解析は未実行。 |

## 5 Why

1. なぜアクティブstudy操作が失敗したか → COM が ActiveX 429 を返したから。
2. なぜ429か → Synergy COMサーバがアクティベーション要求を処理できなかったから。
3. なぜ処理できなかったか → UIスレッドがモーダルループに入っていたから。
4. なぜモーダルか → mshtml のスクリプトエラーダイアログがメインウィンドウを無効化していたから。
5. なぜ解消しなかったか → 閉じても別ハンドルで再生成される発生源が生きており、かつGUIモーダル状態を監視する仕組みが無かったから。

## ロジカルツリー（「MCPでMoldflowを操作できない」の分解）

- ネットワーク到達不可 → **否定**（ping/3389/5683 応答、8765のみ閉）
- ブリッジ未起動 → **一部真**（起動で解決したが429は残存）
- COM未登録 → **否定**（`CreateObject` 自体は成功）
- ビット数不整合 → **否定**（0.8.5 はアクティブstudy系を全て `bitness=64` で実行）
- セッション不一致 → **否定**（MCPもSynergyも SessionId=1）
- **GUIがモーダルで応答不能 → 真因**
- ライセンス不足 → 未検証（今回症状と不一致のため除外）

## Countermeasures

1. ブリッジ健全性チェックに「セッション1でのメインウィンドウ `IsWindowEnabled`」を追加する。
2. 対話セッションで動かす診断ヘルパは `PostMessage` のみを使い、`SendMessage`/`SendKeys` を使わない。
3. ダイアログを閉じた後にハンドルが変化したら、再試行せずアプリ再起動へ切り替える。
4. 対話タスクの待ち時間は最低120秒を見込む（初回の `Add-Type` コンパイルで60秒近くかかる）。
5. 再起動後は `has_project` を確認し、プロジェクト復帰までを1セットの手順として扱う。

## Forbidden

- ポートがLISTENINGなだけで「MCP稼働＝制御可能」と報告すること。
- モーダルが疑われる状態で `SendMessage` / `SendKeys` を送ること。
- 429 を見て、根拠なくCOM再登録やレジストリ変更に進むこと。
- 未保存作業の有無を確認せずに Synergy を強制終了すること。

## 訂正追記（2026-07-25、ユーザー指摘を起点とした再調査）

ユーザーから「box_study_3 でメッシュを生成していたようだ」と指摘され、再調査したところ**真因が一段深いことが判明**した。

### 追加の観測事実

| 項目 | 値 |
|---|---|
| synergy.exe APPCRASH 件数 | 48時間で **41回** |
| シグネチャ（全件同一） | app 9.3.4.0 / module `MFC80U.DLL` 8.0.50727.6229 / `0xc0000005` / offset `0x6c372` |
| 私の操作中の発生 | 10:19:02, 10:19:46, 10:20:27, 10:21:28, 10:22:13, 10:23:48, 10:24:28（`probe_com` / `inspect_active_study` 実行中） |
| クラッシュしたPID | 7264 / 12380 / 19012 / 18940 — **いずれもGUIのPID 6688ではない** |
| 復旧後 | 10:24:28 以降クラッシュゼロ |

### 訂正後の因果連鎖

GUIインスタンスがモーダルで固まりCOM要求に応答しなくなる → `CreateObject("synergy.Synergy")` のたびに**別の synergy.exe が新規起動**される → その新規インスタンスが `MFC80U+0x6c372` で即クラッシュ → 呼び出し側は ActiveX 429 または30〜150秒の待ちを観測する。「スクリプト エラー」ダイアログは可視化された症状であって発生源ではない。

### 追加対策

- 429 を見たら **`CreateObject` をリトライしない**。リトライのたびに落ちるインスタンスが増えるだけで、状況を悪化させる。
- COM操作の前提条件を「セッション1にメッセージポンプが生きている Synergy がちょうど1つ存在する」と定義し、`IsWindowEnabled` で先に検証する。

### メッシュ喪失の有無（結論: 保存済み）

| 項目 | 値 |
|---|---|
| 実体 | `C:\mf\wfe\box_study_3.sdy`（プロジェクト `FE100436`。Warpではない） |
| サイズ / 保存時刻 | **191,781 B / 10:54:25** |
| 同プロジェクトの他スタディ | 4 KB〜27 KB（box_study 27,061 / box_study_1 27,082 / box_study_2 25,946） |
| AMIクローズ時コピー | `#box_unv#.sdy` 等を 10:54:46〜47 に生成 |
| Synergy強制終了 | **10:58:26**（保存の約4分後） |
| メッシュ系プロセス | 強制終了前チェック・事後確認とも `synmesh`/`runstudy`/`cscript` ゼロ |

10:52 にハングした `SendKeys` ヘルパを停止したことでキュー済みのENTERがモーダルに届き、保存とクローズが完了したと解釈するのが最も整合的。**ただしメッシュの中身（ノード数・要素数）は未検証**であり、プロジェクトを開いた上で `moldflow_inspect_active_study` による数値確認が必要。

## Scope limits

MCP経由での**プロジェクトを開く操作は未実証**。Synergyは無プロジェクト状態で復帰しており、`moldflow_open_study_by_name` は仕様通り `NO_PROJECT` を返す。デプロイ版ブリッジに単体のオープンプロジェクトツールは無く、ソース内で `Synergy.OpenProject` は「2010ではハングする」と注記されている。
