# EVO CPU/RAM誤判定と再発防止 — 2026-10-18

Incident: EVO-RESOURCE-20261018. Beads: Clawdbot_Docker_20260125-duwz.

## 誤りと影響

単発のWin32_Processor.LoadPercentage=96を根拠にCPU余力がないと断定した。後続の同時期観測では同指標99%、PerfOS ProcessorのProcessor Timeは61%で食い違った。測定窓・正規化・指標の違いを解消せず、18設定スレッドと32論理CPUから一意の余力も推定できない。16物理コアは32論理CPUで共有される。追加OpenFOAM投入可否の説明に過大な確信があった。新規OpenFOAMは未投入。

Windows利用可能RAM約31.6GiBを搭載RAMと混同した。2026-10-18 21:54:42 +09:00、EVO直接SSH/CIMのDIMM Capacity合計は64GiB、Windows可視は33,184,580KiB（約31.65GiB）、WSL設定はmemory=20GB、processors=24、swap=8GB。64GiBをFEMへ開放した状態ではない。DIMM情報はファームウェア報告値であり、物理実装容量の絶対的保証ではない。約32GiBの差の原因は未確定。GPU/UMA予約、起動上限、ファームウェア報告を候補として調べ、原因を断定しない。

21:51–21:53 JSTの直接procfs/ログ確認ではP1r43fが12スレッド、P1r44fが6スレッドで稼働しログ更新あり。44f旧panel-status.jsonは20:18の異常終了を表示したまま。古い管理ファイルと現行の実プロセスは別レイヤーとして扱う。これは歴史的観測であり、次回は再照会必須。

## 実行した改善

1. `scripts/evo_resource_preflight_20261018.ps1`を追加。搭載DIMM合計、Windows可視/空き、物理コア/論理CPU、WSL設定と実効CPU/メモリ、時刻・取得元を同じレポートに保存する。
2. 簡易LoadPercentageとProcessor Timeを異なる指標として明示。vmmemWSLのCPU時間差分を実測秒数とホスト論理CPU数で正規化し、比較の補助値とする。配置済みスレッド数を稼働率に置換しない。
3. 搭載/OS可視RAMの大きな差、WSL照会失敗時は追加FEM判断を保留。良好な結果でもケース別メモリ予算とネイティブチェックポイントの確認が必要。WSL内availableとWindows空きを合算しない。
4. グローバル指示とauto-memoryに同じ確認順序を追加。稼働中の計算を停止せず、WSL再起動・BIOS変更・メモリ上限変更は実行しない。

## 未解決の是正項目

- 約32GiBがWindowsから利用不能である原因を、GPU/UMA予約・ブート上限・ファームウェア情報で切り分ける。稼働計算のチェックポイントと保守タイミングを確認するまで再起動しない。
- 44fの管理状態と現行プロセスの所有者/試行番号を照合し、古いステータスで現行計算を停止・再起動しない。
- CPU/メモリ予算、温度、空きストレージとケース再開手順を確認するまで重い計算を追加しない。

## 再利用する判断手順

毎回、時刻付きの直接実測 → CPU物理/論理/WSL割当/実負荷を区別 → RAM搭載/OS可視/空き/WSL上限・実効を区別 → 不一致を明示 → ケース資源と回復経路を検証 → 投入後実測。単一の高いCPU値や「64GB搭載」だけでは投入可否を決めない。
