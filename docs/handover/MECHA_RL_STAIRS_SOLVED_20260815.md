## 2. 真因は報酬ではなく「機体が自重を支えられない」ことだった

**最重要**。20回以上の報酬調整で動かなかったものが、機体を直した1回で解決した。

決定的だった実測: **平地でゼロ行動(既定姿勢の保持指令のみ)でも1.5秒で胴体zが
0.428m → 0.055m まで潰れる**。方策以前の問題だった。

### (1) 質量が非物理的だった

カプセル体積から逆算した密度:

    upper_leg   8470 kg/m3   <- 鉄鋼 7850 を超える
    lower_leg  10032 kg/m3   <- 鉛 11340 に迫る

2026-07-10 のトップヘビー対策(torso ×0.7 / 脚 ×1.4)が、元から重い脚をさらに
重くしていた。**総質量238kgは保存される設計だったため、総量だけ見ても気づけなかった。**

実在ヒューマノイドとの比較(当機体はリンク全長 1.40m 相当):

| 機体 | 身長 | 質量 | kg/m |
|---|---|---|---|
| Unitree G1 | 1.27 m | 35 kg | 27.6 |
| Unitree H1 | 1.80 m | 47 kg | 26.1 |
| Honda ASIMO | 1.30 m | 54 kg | 41.5 |
| BD Atlas | 1.50 m | 89 kg | 59.3 |
| **当機体(旧)** | 1.40 m | **238 kg** | **170.0** |

### (2) PDゲインが不足していた

KP/質量が **1.26**(G1 は **4.29**)。単脚支持の重力トルク(モーメント腕0.10mで
233 N·m)にPDが釣り合うには膝の偏差 44.6° が必要だが、膝の可動域は 40° しかない。
膝が限界まで折れて支えられない。追従誤差が全区間 20〜80° だったのはこのため。

### 対処

`train_v50_walk_tracking.py` の2箇所のみ:

- `MASS_REDIST` に `_MASS_SCALE=0.2521` を掛け **238.0 → 60.0 kg**
  (重心を下げる ×0.7/×1.4 の比は保持。腕は従来等倍だったので明示的に係数付与)
- `KP` を G1 の KP/質量比 4.29 に合わせ一律 ×0.857(膝 300→257)
- `KV` は減衰比 ζ ∝ KV/√(KP·m) を保存し ×0.465

修正後、ゼロ行動4秒で潰れず(胴体z 0.40-0.57 維持、upright 0.978-0.992)。

## 6. 方法論(最も再利用価値が高い)

### RL学習が進まないとき、報酬を触る前に測る4項目

1. **静的保持テスト**: ゼロ行動(既定姿勢の保持指令のみ)で自重を支えられるか。
   潰れるなら方策以前の問題。
2. **質量・寸法の妥当性**: 実在機と kg/m 等の無次元量で比較する。
   **総質量だけ見ても再配分バグは見つからない**ので、必ずリンク体積から密度を逆算する
   (鉄鋼 7850 を超えたら異常)。
3. **KP/質量比**: 実績のある機体(unitree_rl_gym G1 は 4.29)と同オーダーか。
4. **タスクの到達可能性**: 目標地物までの距離 ÷ 指令速度 < エピソード長 か。
   満たさなければ、その地形用の報酬は一度も発火しない。

### 外部調査は「公開実装の設定ファイルとの数値比較」だけが効く

- **効いた**: `unitree_rl_gym` の `g1_config.py` と `reward_scales` / `stiffness` を
  機械比較 → `alive` 欠落と KP/質量比の不足を発見。実在機の公表スペックとの
  kg/m 比較 → 質量が3〜6倍過大と判明(3週間の停滞の真因)。
- **効かなかった**: 生体力学文献から5ルールを自前実装(2026-07-27)、CMUモーション
  キャプチャの導入。原理を報酬項へ翻訳する過程でバグが入る(本セッションで2件混入)。
- 象徴的な例: 単脚支持率は文献調査+5ルール実装では 0.35-0.67 のまま動かなかったが、
  **質量を直したら報酬調整なしで 0.92** になった。

参照リポジトリは `D:\RobotAI\repos\` に clone 済み(`legged_gym` / `unitree_rl_gym`、
参照専用)。

### 判定は必ず実測で行う

学習時の `return` はタスク成功の指標にならない。実例:

- v19 継続で `return` 19.6 → 28.5 と上昇したが、登坂成功率は 85.2% → 13.3% に激減。
- 良好なチェックポイントは**その場で** `known_good/` へ退避すること
  (`latest.pt` は上書きされ、RL は単調に改善しない)。本セッションで2回救われた。

判定に使う実測スクリプト(`D:\Temp\...\scratchpad\` に残置、必要なら再利用):

- `diag_climb.py` — 何段登れたか / 生存時間 / 到達距離
- `diag_straddle.py` — 片足/両足がどの段に乗ったか、終了時の状態
- `diag_rewards.py` — 全報酬項の寄与
- `diag_lowfall.py` — 終了理由の内訳と `term_low` 発火時の状態

### 効いた対策: push 強度のカリキュラム

`--push-curriculum-frac F` を追加(`train_v50_walk_rsl.py`)。push_vel を学習の
最初の F 割で 0 → 設定値まで線形に上げ、以後維持する。既定 0.0 で無効。

決定的だったのは学習曲線の質的な違い:

    v32(一定push)   it1000 fall 0.95 → it3000 fall 0.97   横ばい
    v33(curriculum) it1000 fall 1.00 → it3000 fall 0.85   最後まで伸び続けた

**時間ではなく「与える順序」の問題だった。** v32 は 6000iter で 0.227 止まり、
v33 は 3000iter で 0.744。

### 効かなかった対策(記録)

- **長時間学習 (v32, 6000iter)**: 1000iter 以降は横ばい。5000iter 分が無効。
  push+DR は 0.227 へ改善したが無擾乱が 0.635 へ悪化するトレードオフ。

### 有力仮説(未検証) — T079ab

段高の計算は `floor(prog/0.3)`。**段の境界では1e-16の浮動小数点差で1段(0.1m)飛ぶ**
(測定で実際に観測: 境界を測定点にすると21点中6点が±0.100m不一致、境界を外すと57点全一致)。

そして prog の値が両者で違う:

    単体     prog = 0.6 + d
    corridor prog = 2.0 + d

同じ物理位置でも浮動小数点表現が異なるため `floor()` の結果が食い違いうる。
`_support_terrain_dz()` は**足の位置**で地形高さを引き、階段登坂中の支持足は常に
段の縁付近にある。1段分ずれた `expect_z` で `term_low` が誤発火する可能性がある。

**検証手順**: corridor の階段登坂中の `term_low` 発火頻度を単体と比較する。
誤発火なら corridor で有意に高いはず。あわせて発火時の支持足 prog を段境界からの
距離で分布を見る。境界付近に集中していれば仮説は裏付けられる。
対策候補は floor 前の微小イプシロン加算、または段インデックスの round 化。
**単体stairsの既存成果に影響するため慎重に。**
