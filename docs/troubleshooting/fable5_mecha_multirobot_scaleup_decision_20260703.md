# Fable5 回答: 30体×5スキル RLスケールアップ アーキテクチャ判断

作成日: 2026-07-03 JST
入力: `docs/troubleshooting/fable5_mecha_multirobot_scaleup_brief_20260703.md`
性格: **Plan(設計判断)**。実装はユーザー承認後に別セッションで実施(CLAUDE.md Surgical Changes原則)。

---

## 0. 基本戦略(全判断の土台): 共通カノニカル骨格

**結論:** 30体が(a)物理パラメータ違いでも(b)異形状メッシュでも、**全機体を同一DOF構成・同一関節順序の標準骨格(カノニカル骨格)にマッピング**し、形状・質量・リンク長のみを機体差分とする。

**根拠:** GPU並列化(vmap/バッチ環境)は骨格構造の同一性が前提。構造を統一すれば(b)は(a)に帰着し、「30体問題」は「30マニフェスト+1パイプライン」に縮退する。ブリーフ§4の前提未確定は、この戦略でどちらに転んでも吸収できる。

---

## 1. シミュレータ/フレームワーク選定

**結論: Genesis 主軸。MJX+Docker(NVIDIA JAX Toolbox)を控え。Isaac Lab 不採用(現時点)。**

**根拠:**
- Genesis は PyTorch/Taichi 基盤で **Windowsネイティブ CUDA が動作** — WSL起動不能(`WSL_E_USER_NOT_FOUND`)という環境制約を回避できる唯一の低摩擦GPU経路。`pip install genesis-world` のみ、既存MJCFロード互換。
- JAX(MJX)のGPU版はWindowsネイティブ非対応 → Docker JAX Toolbox経由のみ。動くはずだが摩擦が1段多い。控えとして保持。
- Isaac Lab は Isaac Sim 本体が重量級。16GB VRAM単騎(Blender/Cursor同居)+WSL不調環境ではリスク対効果が悪い。カノニカル骨格・マニフェストは Isaac Lab 移行時もそのまま使えるため、後日の移行余地は残る。

**次アクション:** Genesis インストール → 溶接済みV50 MJCF ロード+PPO 1000step のGPUスモークテスト。bd `Clawdbot_Docker_20260125-q00`(DiffMimicスモーク)より先にこれを実施。失敗時のみ Docker JAX Toolbox 経路(GPU handover §Commands To Try Next)へ。

### ⚠️ 先送り不可の設計ギャップ: DOF不足

現行 MJCF/URDF は**全関節 axis="1 0 0"(矢状面のみ)の12DOF**。walk/run/stand/sit は矢状面で成立するが、**「ドアを開く」は肩外転・ヨー+手先把持点が物理的に必須で、現構成では原理的に不可能**。

→ カノニカル骨格確定時に **肩3DOF化+手先接触ジオム** を織り込むこと。骨格を後から変更すると全学習資産(方策・参照モーション・discriminator)が無効化するため、**これは全タスクに先行して確定すべき唯一の仕様項目**。

## 2. マルチスキル方策設計

**結論: スキル条件付き単一方策** — one-hotスキルID+機体形態ベクトル(質量/リンク長等の正規化ベクトル)を観測に注入した multi-task PPO+**条件付きAMP discriminator**。フルASE(潜在スキル空間学習)は第2段階に保留。

**根拠:**
- スキル毎×機体毎の個別方策=150学習ジョブは16GB単騎で非現実的。
- 条件付き単一方策なら学習ジョブは論理的に1本。機体差はドメインランダム化として毎エピソード抽選すれば「30体同時」が自然に実現する(バッチ内に30形態が混在)。
- 5スキル程度の離散セットなら one-hot 条件付けで十分。フルASEの潜在空間は数十〜数百モーション規模で真価を発揮する手法であり、現段階では過剰。

**段階実行:**
- **Stage A**: V50単機体×walk を DiffMimic/トラッキングで検証(物理・リグ妥当性の最安確認)
- **Stage B**: 5スキル参照モーション調達 — walk/run=100STYLES(CC BY 4.0)、sit/stand/door-open=MoMask生成→CLoSD物理化
- **Stage C**: 条件付きAMPで統合学習(このときバッチに機体形態ランダム化を混ぜて30体対応)

## 3. 機体非依存パイプライン改修

**結論: リグ・マニフェスト(スキーマ駆動)方式。** 機体ごとにYAML 1枚: カノニカルボーン名→実メッシュ名マッピング、関節ピボット、軸、可動域、質量、接触面。`v50_*.py` のハードコードリストを全てマニフェスト参照に置換。

**根拠:**
- `TORSO`/`geometry_0.005` 等の固定名はPartPacker出力ごとに無効化する — 30体展開の直接の障壁。
- [T044](部位誤認)・[T046](未溶接・脱離の見逃し)は「機体ごとの手作業分類ミス」が根本。**インテークゲート**(溶接検査→部位自動分類→接合ゲート→人間承認、機体1体につき1回)として形式化すれば構造的に再発を防げる。マッピング不能な機体はインテークで棄却する。

**実装順:**
1. `mecha_rig_manifest.yaml` スキーマ定義(カノニカル骨格仕様を含む — §1のDOFギャップ解消をここで確定)
2. V50を最初のマニフェストとして手書き(=正解データ第1号。Q4の腕再接合作業と兼用)
3. `v50_joint_attachment_gate.py` をマニフェスト読み込み式に一般化(INC-140強化版が土台)
4. エクスポータ群(URDF/MJCF/参照モーション)を一般化。既存 `v50_*.py` は互換ラッパーとして残す

## 4. 着手順序

**結論: V50単機体の残課題を先に完了(並行リファクタ禁止)。ただしスコープは「腕再接合+カメラ修正+強化ゲート再PASS」に限定。** 左手ミラー等の磨き込みはStage A以降に回す(door-openで手先が要るまでは低優先)。

**根拠:**
- [T035]→INC-140 でゲートfalse-PASSが**2回再発**した直後。検証系が信頼できる状態で1機体を通し切ることが30倍スケールの前提(壊れた基盤の複製は欠陥を30倍にする)。
- V50腕再接合はそのまま「マニフェスト第1号の正解データ作り」を兼ねるため二度手間にならない。

**実行キュー(直列):**
1. KEEP_ORIGINAL V50 基準の腕再接合(`D:\AI\PartPacker\output\KEEP_ORIGINAL_..._v50_BASELINE\robot_walk.blend` 参照)
2. カメラ縦クロップ修正(`v50_final_walk_preview.py:229`、`sensor_fit="VERTICAL"` 系)
3. 強化済み接合ゲートで PASS 確認(INC-140版: rest_tol 6% + 直接親子接触チェック)
4. Genesis GPU スモーク(§1)
5. カノニカル骨格仕様+マニフェストスキーマ確定(§3) — **肩3DOF化をここで織り込む**
6. Stage A→B→C(§2)

## 5. リスク覚書(FMEA要点)

| リスク | 影響 | 手当て |
|---|---|---|
| Genesis がこの環境のRTX 5060 Ti(Blackwell)で不安定 | Stage A遅延 | 控えのMJX+Docker JAX Toolbox経路へ即切替(検証コマンドはGPU handover記載済み) |
| 骨格仕様を早期凍結後に不足発覚(指DOF等) | 学習資産の無効化 | 凍結前にdoor-openの把持要件だけはプロトタイプで確認(把持は固定コンストレイントで代替可か) |
| 30体の部位自動分類の誤り | T044/T046の再発×N | インテークゲートで人間承認を機体1体1回必須化(全自動化しない) |
| VRAM 16GBをBlender/Cursorと取り合い | 学習速度低下/OOM | 学習ジョブ実行中はBlender/Cursor停止を運用ルール化 |
| sit/door の参照モーション品質不足(MoMask生成物) | スキル品質低下 | CLoSD物理トラッキングを挟み、非物理フレームを除去してから採用 |
